# Creating Tempo benchmark suites

The directory name is `integrations/tempo`.

This guide covers generating new suites directly from a running Tempo node. For
EEST-derived suite generation, see `integrations/tempo/CREATE_SUITES_EEST.md`.

## What gets generated

Tempo suites are generated by running workloads against Tempo, recording the
canonical blocks that Tempo accepted, and exporting those blocks as a portable
Benchmarkoor Engine suite.

The generated suite directory contains:

- `manifest.json`: Benchmarkoor suite metadata and ordered Engine API calls.
  Benchmarkoor reads it as the suite entrypoint; it contains the suite identity,
  chain/genesis reference, defaults, test metadata, and the setup/test block
  calls to replay.
- `genesis.json`: genesis file used to start the replay node.
- `blocks/*.rlp`: raw block payloads replayed through `reth_newPayload`.
- `blocks/*.bal`: block access lists replayed with each payload when enabled.

Benchmarkoor replays `setup` calls without measuring them and measures only the
`test` calls. When exporting a Tempo block range, blocks before `--from-block`
become setup and blocks from `--from-block` through `--to-block` become the
measured test.

## Export from Tempo

Start or reuse a Tempo node that has already produced the workload blocks you
want to benchmark. The exporter reads from its JSON-RPC endpoint and requires
`debug_getRawBlock`; it also calls `debug_getRawBlockAccessList` unless
`--no-block-access-lists` is set.

Run `export-suite.py` from the repository root:

```sh
./integrations/tempo/export-suite.py \
  --rpc-url http://127.0.0.1:8545 \
  --genesis /absolute/path/to/tempo/crates/chainspec/src/genesis/dev.json \
  --out integrations/tempo/suites/my-new-suite \
  --name my-new-suite \
  --description 'Tempo workload replay' \
  --from-block FIRST_WORKLOAD_BLOCK \
  --to-block LAST_WORKLOAD_BLOCK \
  --tag tempo-native \
  --origin-kind tempo-native \
  --revision TEMPO_REVISION \
  --hardfork dev-all \
  --chain-id 1337 \
  --force
```

Choose `--from-block` as the first block whose execution should be measured. If
the node has warmup or initialization blocks before that point, include them by
setting `--to-block` to the last workload block and leaving `--from-block` after
the warmup prefix.

Benchmarkoor-facing options:

- `--name VALUE`: suite name stored in `manifest.name`; used in suite identity
  and reports.
- `--description VALUE`: human-readable suite description stored in the
  manifest.
- `--metadata KEY=VALUE`: suite-level labels stored in `manifest.metadata`.
  Repeat it for each field. Benchmarkoor surfaces these as metadata labels for
  run/suite context, filtering, and comparisons.

  ```sh
  --metadata workload=tip20-full-block \
  --metadata sender_count=10 \
  --metadata recipient_pattern=shared-existing \
  --metadata gas_target=500M
  ```

- `--tag VALUE`: per-test tag stored in `tests[].tags`. Benchmarkoor uses tags
  for test filtering and markdown `Results by Suite Tag` rollups. Tags are not
  metadata labels.
- `--seed VALUE`: provenance stored in `origin.seed`; it does not seed the
  workload generator.
- `--revision VALUE`: record the Tempo or workload generator revision in
  `origin.revision`.
- `--hardfork VALUE` and `--chain-id VALUE`: record replay chain details in
  `manifest.chain`.

Exporter-only options:

- `--no-block-access-lists`: export only raw blocks when block access lists are
  unavailable or not needed.
- `--force`: replace an existing `manifest.json` and regenerate `blocks/`.

## Where to save suites

Checked-in suites live under:

```text
integrations/tempo/suites/
```

Use a stable, descriptive directory name:

```text
integrations/tempo/suites/<suite-name>/manifest.json
integrations/tempo/suites/<suite-name>/genesis.json
integrations/tempo/suites/<suite-name>/blocks/
```

## Replay a generated suite

Run a focused suite:

```sh
TEMPO_SUITE_DIR=/absolute/path/to/benchmarkoor/integrations/tempo/suites/my-new-suite \
TEMPO_IMAGE=docker.io/tempoxyz/tempo:latest \
docker compose -f docker-compose.tempo.yaml run --rm benchmarkoor
```

Run the aggregate `all` suite with boundary resets:

```sh
TEMPO_SUITE_DIR=/absolute/path/to/benchmarkoor/integrations/tempo/suites/all \
TEMPO_ROLLBACK_STRATEGY=container-recreate \
TEMPO_IMAGE=docker.io/tempoxyz/tempo:latest \
docker compose -f docker-compose.tempo.yaml run --rm benchmarkoor
```

`TEMPO_ROLLBACK_STRATEGY=container-recreate` means Benchmarkoor recreates the
Tempo container at suite segment boundaries instead of trying to rewind the same
node. Use it for merged suites because each source suite starts from genesis.

## Add a new suite to `all`

If the checked-in per-source suite directories are present, add the new
`manifest.json` path to `integrations/tempo/merge-all-suites.sh`, then run:

```sh
./integrations/tempo/merge-all-suites.sh
```

`merge-all-suites.sh` calls:

```text
integrations/tempo/merge-suites.py --copy-files ...
```

The `--copy-files` flag is important. It copies referenced block files into
`integrations/tempo/suites/all/blocks/` and rewrites manifest references to
`blocks/...`. Without that, `all` can contain `../other-suite/...` references
that work locally but fail inside Benchmarkoor Docker because only the selected
suite is mounted at `/app`.

Use `--exclude-test '<source test name>'` when replacing an older case in an
aggregate while keeping it in its original source suite.

## Validate before committing

Run `./integrations/tempo/validate-suite.py` against each changed suite, such as
`integrations/tempo/suites/my-new-suite` and `integrations/tempo/suites/all`.

For a new or changed focused suite, run that focused suite with Benchmarkoor.
Do not run the large `all` suite unless the task specifically requires it.

## Commit checklist

Before committing:

- The suite directory has `manifest.json`, `genesis.json`, and every referenced
  block file.
- `manifest.json` has the intended `name`, `description`, `tags`, and metadata.
- If included in `all`, the aggregate has no `../` file references.
- Counts in `integrations/tempo/README.md` and `integrations/tempo/REPORT.md`
  match the manifests.
- `git status --short` contains only intended Benchmarkoor changes.
